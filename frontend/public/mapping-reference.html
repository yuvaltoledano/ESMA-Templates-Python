Reference

From an ESMA pool to a MILAN pool

This document describes exactly what the ESMA → MILAN tool does to a residential mortgage pool reported in the ESMA Annex 2 (RRE) loan-level templates when it produces the Moody's MILAN input file. It is written for the person preparing or reviewing the pool, not for the person maintaining the software.

Part A · The pool

Nine steps that decide which loans and properties are in, which identifiers and valuations are used, how shared collateral is grouped and how value is allocated to each loan. Read once, in order.

Part B · The columns

All 175 MILAN columns, each with its ESMA source, its rule and what happens when the input is missing. Searchable by MILAN header or ESMA field code. The code maps and the harder derivations have their own sections.

Part C · The summary

How each line of the Execution Summary sheet is calculated and what the other sheets of the workbook contain.

Part D · The checklist

What makes a run stop, what makes it warn, and which ESMA inputs end up as "ND" in MILAN. Read before submitting a pool.

Conventions used here

  • ESMA fields are named by code and template name, for example RREL30 Current Principal Balance. Codes starting RREL are in the loans file, codes starting RREC in the collaterals file.
  • MILAN columns are named by their exact header in the output, for example Loan CB, with their position (1 to 175) in the column index.
  • Fields the tool computes itself carry a calc_ prefix in the workbook, for example calc_aggregated_property_value. They appear in the "Combined flattened pool" sheet and again in MILAN's "Additional data" columns.
  • "Missing" means a cell that was empty, NA, ND or ND1 to ND5 in the ESMA file. "ND" in bold quotes means the literal text the tool writes to MILAN.
  • Worked examples use the tool's built-in synthetic test pool: 8 loans, 12 collateral rows, cut-off date 2024-06-30, one example of every collateral structure. Every number shown is what the tool produces for that pool.

What the tool produces

One Excel workbook named <cut-off date> <deal name> Flattened loans and collaterals.xlsx with ten sheets. Sheet 10, "MILAN template pool", is the MILAN input: one row per loan, 175 columns, every cell written as text. Sheet 1 is the Execution Summary. Sheets 2 to 9 are the audit trail: the cleaned inputs, the identifier mapping tables, the group classifications and the flattened pool that MILAN is built from.

Part A

What happens to the pool

Before any MILAN column exists, the tool has to decide which rows count, which of the duplicated ESMA identifiers to trust, which of the two valuations on each collateral row to use, and how to turn a many-to-many loan–property structure into one row per loan. These nine steps are that decision chain.

Step 1

The two files and how they are read

The tool reads the loans file and the collaterals file as exported from the securitisation repository, renames the ESMA field codes to readable names, types the numeric fields from the ESMA taxonomy, and normalises the dates.

What the files look like

Both files are CSVs with one column per ESMA field, headed by the field code: RREL1 to RREL84 in the loans file, RREC1 to RREC23 in the collaterals file. Repository exports also carry a Sec_Id column, a Pool_Cutoff_Date column and, next to every monetary field, a currency companion column named with the suffix _CURRENCY (for example RREL30_CURRENCY).

Each field code is renamed to the field name in the ESMA RRE taxonomy, then lower-cased with underscores: RREL30 becomes current_principal_balance, RREC13 becomes current_valuation_amount. Columns the taxonomy does not know keep their name, cleaned the same way (Pool_Cutoff_Date becomes pool_cutoff_date). These cleaned names are the headers you see in the audit-trail sheets.

Missing values

Eight tokens mean "no data" and are read as missing: an empty cell, NA, ND, ND1, ND2, ND3, ND4 and ND5. The distinction between the ND reasons is not carried forward: whatever the reason, a missing value reaches MILAN as "ND". A cell that contains only spaces is also treated as missing wherever a rule tests for missing data.

How values are typed

  • Amounts, percentages and counts. Every field the ESMA taxonomy formats as {MONETARY}, {PERCENTAGE} or {INTEGER-n} is read as a number. Surrounding spaces are ignored. A value in such a field that is not a number and not a missing-value token stops the run with a message naming the file, the field, the row and the value. Nothing is silently dropped.
  • Identifiers. RREL2 to RREL5 and RREC2 to RREC4 are always read as text, so an identifier such as 007 keeps its leading zeros.
  • Everything else (codes, names, flags) is read as text.
  • Character encoding. A file that is not valid UTF-8 is repaired field by field (UTF-8, then Windows-1252, then Latin-1, then unreadable bytes are dropped), so a Windows-exported file with accented names loads without manual conversion.

Columns that are dropped

  • Sec_Id, RREL1 / RREC1 Unique Identifier and RREL6 Data Cut-Off Date: they identify the submission, not a loan.
  • The currency companions of fifteen loan fields (RREL16, 20, 29, 31, 32, 33, 39, 41, 61, 64, 67, 71, 73, 74, 77) and three collateral fields (RREC13, 17, 21). The pool is treated as single-currency. One companion is kept: RREL30_CURRENCY, which becomes MILAN's Loan Currency.

Dates

Date fields often arrive in two forms at once, ISO text (2023-12-31) and Excel serial numbers (45291), typically because the file was opened and re-saved in Excel. The tool accepts both: ISO dates written YYYY-MM-DD or YYYY/MM/DD (a time after the date is ignored), and whole or decimal serial numbers that fall between 1900-01-01 and 2100-01-01 (counted from Excel's 1899-12-30 origin). Anything else becomes missing, and a warning lists up to five of the offending values per column.

This applies to all sixteen loan-side date fields (RREL7, 8, 9, 23, 24, 36, 51, 53, 55, 60, 62, 63, 65, 66, 72 and Pool_Cutoff_Date) and to RREC15, RREC19 and RREC20 on the collateral side. RREL65 Date of Restructuring may contain several dates separated by commas or semicolons, as the ESMA schema allows; the tool keeps the latest one.

The pool cut-off date

The first non-missing Pool_Cutoff_Date in the loans file names the output workbook and anchors the Execution Summary. Seasoning and the arrears-timing columns use each loan's own cut-off date value, which in a normal export is the same date on every row.

The run stops here when
  • a numeric field holds a non-numeric value (the message names file, field, row and value);
  • a file has a header but no data rows;
  • two columns end up with the same name after renaming;
  • a required column is absent. Loans: RREL2, RREL3, RREL5, RREL23, RREL30, RREL69 and Pool_Cutoff_Date. Collaterals: RREC2, RREC4, RREC5, RREC9 and RREC13;
  • no row in the loans file carries a cut-off date.

Any other field may be absent or partly missing. An absent field that MILAN needs is treated as missing on every row and announced in a warning (see the global rules).

Step 2

Which loans and properties are kept

Only active loans with a positive balance enter the pool, and only real-estate collateral rows that back one of those loans and carry a usable valuation.

Loans

A loan row is kept when both hold:

  1. RREL69 Account Status is one of PERF (performing), ARRE (in arrears), RARR (restructured, in arrears) or RNAR (restructured, no arrears). Defaulted, redeemed and repurchased loans leave the pool here.
  2. RREL30 Current Principal Balance is greater than zero. A missing balance fails this test.

Collateral rows

A collateral row is kept when all four hold:

  1. RREC9 Property Type is present.
  2. RREC5 Collateral Type is not one of the nineteen non-property codes: guarantees (GUAR), vehicles (CARX, CMTR, RALV, NACM, NALV, AERO, OTHV), equipment (MCHT, INDE, OFEQ, ITEQ, MDEQ, ENEQ, OTHE), financial assets (SECU, OTFA), and inventory or individual items (OTGI, INDV). Any other code passes, including RBLD, CBLD, IBLD, OTRE, MIXD and OTHR.
  3. RREC2 Underlying Exposure Identifier matches a kept loan under either identifier convention (RREL2 original or RREL3 new). The tool has not yet chosen between the two conventions, so it accepts both here.
  4. At least one of RREC17 Original Valuation Amount and RREC13 Current Valuation Amount is greater than zero.
Why loans go first

The surviving loans decide which collateral rows survive. A collateral row whose loan has been excluded has nothing to secure in this pool, so it is dropped with the loan rather than kept as an orphan.

The run stops here when

no collateral row survives.

Worked examplesynthetic pool

All 8 loans are PERF or ARRE with positive balances and all 12 collateral rows are RES property rows with positive valuations, so nothing is removed. In a real pool this step typically removes the redeemed and repurchased loans that repositories keep reporting after they leave the pool.

Step 3

Which identifiers are used

ESMA reports every loan, borrower and collateral under two identifiers, "original" and "new". The tool picks one of each pair and keys everything on it.

The loan identifier

The loan identifier is the join between the two files, so its selection is strict. The candidates are RREL2 Original Underlying Exposure Identifier and RREL3 New Underlying Exposure Identifier; the chosen one becomes calc_loan_id and MILAN's Loan Identifier.

  1. Uniqueness. A candidate is disqualified if any non-missing value appears on more than one loan row, or if every value is missing.
  2. Coverage. For each remaining candidate, coverage is the share of its distinct values that appear as RREC2 in the kept collateral rows. 100% means every loan has at least one collateral row.
  3. Choice. One survivor: it wins. Both at 100%: original wins. Exactly one at 100%: it wins. Both partial but different: the higher wins. Both partial and equal: original wins and a warning lists unmatched identifiers from both.
  4. Threshold. If the winner's coverage is below the minimum coverage setting (0.85 unless you change it on the page or the command line) the run stops. Between the minimum and 100% the run continues with a warning that lists up to ten unmatched identifiers.

Loans whose chosen identifier is missing are dropped with a warning. Then both files are cut to their intersection: a loan without any collateral row is dropped, and a collateral row whose loan is not in the pool is dropped.

Borrower and property identifiers

Duplicates are expected here (one borrower has several loans; one property backs several loans), so the rule is simpler: whichever of the pair has more distinct non-missing values wins; on a tie, or when the two columns are identical, the original wins.

BorrowerRREL4 Original Obligor Identifier vs RREL5 New Obligor Identifier → calc_borrower_id, MILAN Borrower Identifier PropertyRREC3 Original Collateral Identifier vs RREC4 New Collateral Identifier → calc_property_id, and for the main property MILAN Property Identifier
The run stops here when
  • both loan-identifier columns are unusable (duplicates, or entirely missing);
  • the chosen loan identifier's coverage is below the minimum coverage setting;
  • no loan or no collateral row remains after the intersection.
Worked examplesynthetic pool

The collateral rows reference the new identifiers (NEW_001 …). RREL2 is unique but has 0% coverage; RREL3 is unique with 100% coverage, so RREL3 wins and calc_loan_id is NEW_001 to NEW_008.

Borrowers: RREL4 and RREL5 both have six distinct values, so the original BORIG_01 … is used. Properties: both have eight distinct values, so PORIG_01 … is used. That is why the MILAN output keys loans on NEW_ identifiers but borrowers and properties on ORIG ones.

Step 4

Which valuation is trusted

Every collateral row carries two valuations, original and current, each with a method, an amount and a date. One of them is chosen per row, and its method, amount and date always travel together.

  1. Prefer a full inspection. If RREC14 Current Valuation Method is FIEI (full, internal and external) or FOEI (full, external only), take the current valuation (RREC13 amount, RREC14 method, RREC15 date). Otherwise take the original valuation (RREC17, RREC18, RREC19). A recent drive-by, desktop, indexed or automated value does not displace a full inspection at origination.
  2. Reject an implausible amount. If the amount chosen in step 1 is missing or at most 10, switch to the other valuation. This catches zero fills, placeholders and amounts reported in thousands.
full_inspection = current method in {FIEI, FOEI} chosen = current if full_inspection else original if chosen amount is missing or ≤ 10: chosen = the other one use chosen.method, chosen.amount, chosen.date

The chosen method and date reach MILAN as Property Valuation Type and Property Valuation Date for the group's main property (step 7); the chosen amount feeds the allocation in step 8. Because all three come from the same valuation, MILAN's value, type and date never describe different appraisals.

Step 5

How shared collateral is grouped

A property that secures several loans ties those loans together, and a loan secured on several properties ties those properties together. The tool follows every such link and treats each connected set as one collateral group.

Each kept collateral row is one link between a loan (calc_loan_id) and a property (calc_property_id); duplicate links count once. Everything reachable through links, directly or indirectly, forms one group, numbered 1, 2, 3 … in a fixed order so that the same input always gives the same numbering. Every loan and every property belongs to exactly one group, and from here on the tool works group by group.

The five structure types

Each group is classified from its loan count L, property count P and link count E compared with the maximum possible L × P:

Type 1one loan → one property
Type 2one loan → multiple properties
Type 3multiple loans → one property
Type 4full set: every loan on every property
Type 5cross-collateralised: at least one pairing missing

Step 6

Which valuation convention applies

When one property backs several loans, it appears on several collateral rows. Issuers populate the amount on those rows in one of two ways, and the tool has to know which before it can recover the property's value.

by_loan · value repeated

The full property value is written on every row the property appears on. The property's value is the amount on one row (the first non-missing).

by_group · value split

The issuer has already divided the property value across the rows, usually pro rata to loan balance. The property's value is the sum of its rows.

Detection

The tool looks only where the two conventions give different data: properties linked to two or more loans whose balances differ, with at least two non-missing valuation amounts after step 4. For each such property, identical amounts across its rows are a vote for by_loan and differing amounts a vote for by_group. If more than 90% of the votes go one way, that convention is used. Otherwise the detection is ambiguous: the tool uses by_loan and warns. A pool with no multi-loan property is also ambiguous and gets by_loan.

You can override the detection on the page (aggregation: auto, by_loan or by_group) or with the command-line option. The convention actually used is written to the Execution Summary as Aggregation Method.

Why this matters

Reading a by_group file as by_loan deflates every property value; reading by_loan as by_group double-counts it. Neither mistake stops the run; both move every LTV. If the summary shows a convention you did not expect, or the run warns that detection was ambiguous, check the collateral file before using the output.

Under by_loan, if a property's rows carry different non-missing amounts the first one is used and a warning names up to five such properties. Under by_group the rows are summed and nothing is checked.

Worked examplesynthetic pool

PORIG_04 backs NEW_003 (160,000) and NEW_004 (95,000) and carries 400,000 on both rows; PORIG_05, PORIG_06 and PORIG_07 are likewise repeated unchanged. Four votes for by_loan, none against: by_loan is used, and the Execution Summary shows by_loan.

Step 7

Which property represents the group

A MILAN row describes one property. When a group has several, one is chosen as the main property, and every loan in the group reports that property's identifier, type, region, occupancy, valuation type and valuation date.

Within a group, the properties are ordered by the following keys, and the first one wins. A missing value on any key sorts last.

  1. Highest value, using the per-property value from step 6.
  2. Owner-occupied first: RREC7 Occupancy Type equal to FOWN beats any other code.
  3. Full inspection first: the method chosen in step 4 is FIEI or FOEI.
  4. Most recent valuation date, from the valuation chosen in step 4.
  5. Lowest property identifier, alphabetically. This last key guarantees that two runs on the same input choose the same property.

The choice is made once per group, not per loan: in a full set of two loans and two properties, both loans report the same main property even though each is directly secured on both.

Step 8

How value, LTV and seasoning are allocated

The group's collateral is shared out to its loans in proportion to balance. That share is MILAN's Property Value. Two group-level LTVs and a per-loan seasoning are computed alongside it.

Allocated property value

group property total = sum of the per-property values in the group (step 6) group loan total = sum of RREL30 Current Principal Balance over the group's loans allocated(loan) = group property total × RREL30(loan) / group loan total

The allocated values of a group always add back to the group property total. If the group loan total is zero or missing (which step 2 normally prevents) the total is split equally and a warning is issued. The result is calc_aggregated_property_value, MILAN's Property Value and Additional data 10.

Allocation ignores which property a loan is actually on

In a cross-collateralised group every property stands behind every loan, so a loan secured on one property still receives a share of the whole group's value. The individual property values are not preserved on the MILAN row; only the allocated share is.

Group-level LTVs

calc_current_LTV = sum of RREL30 over the group ÷ sum of allocated values over the group calc_original_LTV = sum of RREL29 over the group ÷ the same denominator

Both are the same for every loan in the group, missing balances count as zero, and both are missing when the denominator is zero. They reach MILAN as Additional data 11 and 12. They are not MILAN's Original LTV and Current LTV (columns 120 and 121), which come from the ESMA-reported RREC16 and RREC12 of the main property divided by 100. The Execution Summary's LTV lines use the group-level pair.

Seasoning

calc_seasoning (years) = (pool cut-off date − RREL23 Origination Date) ÷ 365.25

Per loan, missing if either date is missing, negative without warning if origination is after cut-off. MILAN's Additional data 13.

Step 9

The flattened pool

After step 8 the tool has one row per loan. This is the "Combined flattened pool" sheet of the workbook, and every MILAN column is read from it.

Part B

The 175 MILAN columns

Every column of the "MILAN template pool" sheet, in output order. Start with the rules that apply to all of them, then use the index to look up a column by its MILAN header or by the ESMA field it comes from. The code maps and the derivations that need more than a sentence have their own sections.

Part B · Rules

Rules that apply to every column

Five rules decide how a value is written, whatever the column. Read them once; the index assumes them.

  1. Every cell is text. Numbers, dates and flags are all written as strings, so MILAN receives 180000, 2019-03-15 and TRUE rather than typed Excel cells.
  2. Missing is "ND". A value that is missing on the flattened pool (empty, NA, ND, ND1 to ND5 in the ESMA file) is written as the literal "ND". A column whose ESMA source is absent from the file altogether is filled with "ND" for every loan, and the run log carries the warning MILAN mapping: the following source columns are missing and will be set to 'ND': ….
  3. Numbers keep up to 15 significant digits, with no scientific notation, no thousands separators and no trailing zeros: 250980.392156863, 0.69, 0. Percentages that ESMA reports as "69" (meaning 69%) are divided by 100 where the index says so, and arrive as 0.69.
  4. Dates are written YYYY-MM-DD and flags as TRUE / FALSE. A date that could not be read in step 1 is already missing by now and becomes "ND".
  5. A code the tool does not know becomes "ND". Every code-mapped column (Origination Channel, Property Type, Account Status and so on) translates an ESMA list code into a MILAN number through the tables in Code maps. A code that is not in the table, including a mistyped one, is written as "ND" rather than guessed.

Part B · Deep dives

Deep dives

The columns whose rule does not fit in one line of the index. Each one shows the rule, then what the synthetic pool produces.

Ranking, External Prior Ranks CB and Pari Passu (columns 17, 20, 21)

These three columns look across the loans that share a main property (calc_main_property_id). They answer: where does this loan rank, how much senior debt sits outside the pool, and how much equal-ranking debt sits outside the pool.

InputsRREL31 Prior Principal Balances (balance ranking ahead of this loan, in or out of the pool), RREL32 Pari Passu Underlying Exposures (balance ranking equal to this loan, in or out of the pool), RREL30 Current Principal Balance of every loan on the same main property. A missing RREL31 or RREL32 counts as 0 in the arithmetic. RankingLoans on the same main property are sorted by RREL31 ascending and given dense ranks 1, 2, 3 … Equal RREL31 gives equal rank. A loan alone on its property is rank 1. External Prior Ranks CBRREL31 minus the pooled balance of all loans with a strictly lower rank on the same property, floored at 0. Written as "ND" when RREL31 itself is missing. Pari Passu (Not In Pool)RREL32 minus the pooled balance of all loans at the same rank on the same property (including this loan), floored at 0. Written as "0" when RREL32 is missing. Total Prior Ranks CBColumn 18 is RREL31 copied unchanged, so the reader can see the input next to the derived columns.
Worked exampleproperty PORIG_04, two pooled loans
LoanRREL30 CBRREL31 priorRREL32 pari passu
NEW_003160,00050,000250,000
NEW_00495,000210,00095,000

Both loans have PORIG_04 as their main property. NEW_003 reports 50,000 ranking ahead of it; NEW_004 reports 210,000 ranking ahead of it (the 50,000 plus NEW_003's 160,000).

Sorted by RREL31: NEW_003 (50,000) is rank 1, NEW_004 (210,000) is rank 2.

NEW_003: nothing ranks below rank 1 in the pool, so 50,000 − 0 = 50000. All of it is outside the pool.

NEW_004: the pooled balance at rank 1 is 160,000, so 210,000 − 160,000 = 50000. The same external senior loan, seen from the second-ranking loan.

NEW_003: pooled balance at rank 1 is its own 160,000, so 250,000 − 160,000 = 90000 of equal-ranking debt outside the pool.

NEW_004: pooled balance at rank 2 is its own 95,000, so 95,000 − 95,000 = 0.

The Execution Summary's "External Prior Ranks" (100,000.00) and "External Equal Ranks" (90,000.00) are the sums of these two columns over the pool.

NEW_001 reports no RREL31 and no RREL32. It is alone on PORIG_01, so Ranking is 1. External Prior Ranks CB is written "ND" (missing RREL31) while Pari Passu is written "0" (missing RREL32). The two columns treat a missing input differently; the "ND" is excluded from the summary total and the "0" contributes nothing.

Months Current and Months In Arrears (34, 36)

Interest Rate, Full Margin, Margin After Reset Date, Original LTV, Current LTV (30, 31, 32, 120, 121)

ESMA reports percentages as whole numbers: a 2.5% coupon is 2.5, a 69% LTV is 69. MILAN wants fractions. These five columns divide by 100: RREL43 2.5 → 0.025; RREL46 1.2 → 0.012; RREL50; RREC16 69 → 0.69; RREC12 56 → 0.56. A missing input stays "ND". No other numeric column is rescaled; DTI Ratio (56) in particular is copied as reported.

Two LTVs in the file

Columns 120 and 121 are the ESMA LTVs of the main property, divided by 100 and unchanged otherwise. The group-level LTVs the tool computes in step 8 (calc_original_LTV, calc_current_LTV) are in columns 154 and 155 and are what the Execution Summary's "WA Original LTV", "WA Current LTV" and "Current LTV ≥ x%" lines use. Part D

Before you submit a pool

The tool never guesses. A problem it cannot resolve stops the run with a message naming the file, the field, the row and the value; a problem it can live with is logged as a warning and shows in the run's log. This chapter lists both, and the ESMA inputs whose absence silently becomes "ND".

Part D · Checklist

Data-quality checklist

What stops the run

ConditionWhat to fix
A file is empty, or two columns have the same name after renamingExport the template again. Duplicate names usually come from a header both as an ESMA code and as its long name.
A required column is missingThe loans file must carry RREL2, RREL3, RREL5, RREL23, RREL30, RREL69 and the cut-off date; the collaterals file must carry RREC2, RREC4, RREC5, RREC9 and RREC13. The message names the missing column.

What produces a warning

  • A date that could not be read as YYYY-MM-DD or as an Excel date. The value is set to missing and up to five examples are listed. The loan is kept.
  • The loan identifier is populated on fewer than 100% but at least 85% of loans, or both identifier columns have the same coverage (the new identifier wins). Loans without the chosen identifier are dropped and counted.
  • The aggregation convention could not be decided from the data (step 6): by_loan is used. Or the convention is by_loan but a group reports inconsistent amounts.
  • A group's loans have zero balance in total: its value is split equally.
  • A loan secured by more than 50 properties.
  • An ESMA column the mapping expects is absent: the MILAN column is filled with "ND" and the warning names the columns.
  • Two MILAN rows share a Loan Identifier.

ESMA fields that MILAN needs and the templates do not carry

These MILAN columns are "ND" for every loan, whatever the input, because no ESMA Annex 2 field holds the information. If MILAN needs them, they are filled after the tool runs:

Total Prior Ranks OB (19) · Further Advances (23) · Grace Period, Type of Payment Holiday, Length of Payment Holiday Allowed In Months (25–27) · FX Risk Mitigated, Inflation-Indexed Loan, Exchange Rate At Loan Origination (39–41) · Borrower Birth Year (44) · Internal Credit Score, Credit Score - Canada (46, 47) · Number of Borrowers (49) · Guarantor's Income (54) · Loan To Employee, Number of Properties Owned By Borrower (57, 58) · Regulated and the eight adverse-credit columns (59–67) · Purchase Price (71) · Confidence Interval For / Provider of Original AVM Valuation (75, 76) · Rental Income, Metro / Non Metro, Construction Year (79–81) · Mortgage Inscription and Mandate for Property 1 (82, 83) · all of Properties 2 to 5 (84–119) · Additional Collateral Type and Value (124, 126) · Restructuring Type (131) · MIG %, Initial and Current MCI Coverage Amount (141–143) · the six spare columns (170–175).

Checklist

  1. Identifiers. RREL3 (or RREL2) populated on every loan; RREC2 uses the same identifier; RREC4 (or RREC3) populated on every property; borrower identifiers consistent across a borrower's loans.
  2. Dates. YYYY-MM-DD throughout; one cut-off date; origination and maturity on every loan (seasoning, years to maturity and WA metrics depend on them); RREL66 populated on cured loans or Months Current will read "Never in Arrears".
  3. Numbers. No separators or symbols; percentages as whole numbers (2.5 for 2.5%); RREL31 and RREL32 reported as 0, not left blank, on loans with no senior or equal debt, or External Prior Ranks CB will be "ND".
  4. Codes. ESMA list codes exactly as in the taxonomy (upper case, four letters); RREL10 as TRUE/FALSE, RREL76 as Y/N; RREL45 tenor reported whenever the index is LIBO or EURI.
  5. Valuations. Each collateral row with at least one plausible amount (over 10) and its method and date; a full inspection reported as FIEI or FOEI if it should be trusted over the original.
  6. Collateral type. RREC5 a property code on every property row; guarantee, vehicle, equipment and financial-asset rows are filtered out, and a loan left with no collateral row is dropped in step 3.
  7. Read the Execution Summary first, then sheet 9, then the MILAN sheet. The warnings in the run log tell you which loans were dropped and why.
